# API reference and implementation status

Endpoint-by-endpoint detail on what the service does today, and what it does
not yet do. For a plain description of what Kelpie is and how to run it, see
the [README](../README.md); the rest of the documentation is indexed at
[docs/README.md](README.md), and the integrator's summary of the wire
conventions is [agents/api-and-webhooks.md](agents/api-and-webhooks.md).

A key from before this default that has an empty `scopes` is a full-access key. There are three verbs. Write implies read. A delete of an admin or config resource (a webhook, an API key, a custom field, a pipeline stage, a consent purpose, a member, an invitation) needs that resource's write scope. A convert needs the write scope of the source and the write scope of the target type: `POST /v1/enquiries/:id/convert` to a Deal needs `enquiries:write` and `deals:write`. A resolve of an agent task needs `agent_tasks:write` and the read scope of the target type (`dashboard:read` for a workspace task). A run needs those and the write scopes of what the run may write: `notes:write`, the write scope of the target where it has fields to update, `plan_items:write` on a pipeline record or an event, `positions:write` on a person or a candidate, and `decisions:write` when the task has `may_create_decision`. Every MCP tool needs the same scope as its REST route. AI settings and runs need `ai:read`; changing AI settings and person intake need `ai:write`, and each record intake writes also needs that record's own write scope. Every list takes `?limit=`, `?sort=` and `?cursor=`. Cursors are keysets bound to the sort that issued them.

**Id filters repeat to name a set:** `?person_id=per_1&person_id=per_2` matches either, up to 200 ids. It is what replaces the `include` expansion this version does not have: a list page showing a related column resolves it in one extra request rather than one per row. A blank value or more than 200 is `422`.

A job title lives on Position and nowhere else, so a person can hold one at more than one company. `?q=` on people matches the titles they hold and the companies they hold them at, which is what the mockup's filter box does.

Hiring state lives on Candidate, the Person↔Role link, for the same reason: one person can be interviewing for one role and in the nurture pile for another. `interview_stage` is null unless the status is `in_process`, and the API keeps that true — leaving the process clears the stage, rejoining it restores the first one, and a stage that contradicts the status is a `422`.

Forms are the one public surface. Managing them takes credentials like everything else; submitting one takes nothing but the workspace id and the form's `slug` in the URL, because the caller is a stranger's browser on a stranger's website. The slug is not a secret: every page that embeds the form shows it. It is unique in its workspace, and a user can change it or regenerate it. The embed page is addressed by form id, so a pasted snippet never changes, and the page carries the current submit path, so embeds follow a new slug on their own. The page posts to a path on its own origin and holds no URL built from request headers, because shared caches store it. Only a caller that saved the old submit URL gets a `404`. Everything under `/v1/public` is mounted outside the credentialled routes and answers any origin without allowing credentials, so a browser never attaches a signed-in reader's session cookie to one. A submit is **core capture followed by post-submit actions**: the person/company/position upserts are one atomic transaction, and each configured action (create Deal, Opportunity, or Partnership; merge person or company tags; add to a list; attach the submitter to a pipeline record) runs under its own savepoint. An action that fails logs `{action, status, detail}` to `form_submissions.action_log` and the runner continues, so a broken action never loses the visitor's `201`. **A submit never updates a field of a record that already existed.** A mapped answer is written only on a record the submit creates: a new Person, a new Company, a new Position, and the Deal, Opportunity, Partnership or Enquiry a create trigger makes. On a Person matched by email, a Company matched by domain or name, and a Raise the form attaches to, no mapped answer is written: no name part, phone, address, summary, tag (from any field type), custom field, `company.domain` or `do_not_contact`. Each such answer that differs from the stored value logs `{action: "map_field:<target>", status: "skipped", detail: "The record already existed"}`; an answer equal to the stored value logs nothing. Equal means: trimmed text matches exactly (without regard to case for `company.name`, `position.title`, `person.email` and `company.domain`, the last through the domain normaliser); the phone is on the stored list; every tag or list entry is already stored; a boolean or number is the stored one; an address part or a custom field has the stored value. A stored blank and a typed value differ. Every answer stays in the submission's `answers`. A matched record still gets what is not a visitor's value: the Position (a held Position keeps its title), the pipeline, list and attach links, the form's own `person_tags` and `company_tags`, `last_contacted_at`, the timeline entry, and a consent grant where the person has no row for the purpose (a row that exists is never changed). Each mapped answer is also checked against the `PATCH` body of the record it maps to; one that body would refuse is not written and logs the same `map_field:<target>` entry with the schema's reason, and the submit still answers `201`. The mapped values of each new record are written under a savepoint, and a failure there logs `map_fields:<record type>` as `error`. A paused form answers `409`, and answers without a usable address answer `422`. `GET /v1/forms/:id/embed` hands back the iframe and script snippets to paste into a site; the page they point at is server-rendered from the form itself, so embedding it does not pull the CRM bundle into somebody else's marketing site.

**A company is never inferred from an email domain.** Only a field mapped to `company.domain` sets one. An email domain is not a company identifier: one company sends from several, a consumer address belongs to none, and two people at unrelated businesses can share one, so inferring it merges records that were never the same company. A Deal or Partnership belongs to a Company, so a form with `create_deal` or `create_partnership` on and no `company.name` or `company.domain` field is refused at `422` rather than left to quietly never create the records it promises. An Opportunity or Enquiry is exempt because their `company_id` is nullable.

**A form can require a spam check.** With `require_spam_check` on, a public submit must pass four checks. A hidden input must be empty (`trap`). The submit must carry a `token` from `GET /v1/public/workspaces/:workspaceId/forms/:formId/token`, signed by this deployment for this form in the last 24 hours. It must arrive at least `FORMS_SPAM_MIN_SECONDS` after that token was issued. And when the deployment has a CAPTCHA provider (`CAPTCHA_PROVIDER`), it must carry a `captcha_response` that the provider accepts. The Kelpie embed does all of this by itself. A submit that fails is not refused: it gets the same `201`, and it is stored with `status: "spam"` and a `spam_reason`, with no person, no action, no email and no event. `GET /v1/forms/:id/submissions` lists accepted submissions unless `?status=spam` asks for the held ones. `POST /v1/forms/:id/submissions/:submissionId/release` runs the submit rules on the stored answers and makes the submission `accepted`; it is `409` for a submission that is not held. Held submissions older than 30 days are deleted. The setting is off for a form made over the API unless the body sets it, because a site that posts JSON from its own form has no token until it gets one. With the setting off, no check runs.

**A form can send two emails after a submit.** `notify_email` sends a notification to `notify_recipients`: up to 10 of `{ "kind": "member", "member_id" }` (the member's current account email) and `{ "kind": "address", "address" }` (stored trimmed and lowercased). `auto_reply` sends an auto-reply to the address in the `person.email` answer, with an optional `auto_reply_reply_to` recipient. Each email has a subject and a plain-text body template (`notify_subject`, `notify_body`, `auto_reply_subject`, `auto_reply_body`) with `{{form.name}}`, `{{form.title}}`, `{{workspace.name}}` and `{{submitted_at}}`; the notification also takes `{{person.email}}`, `{{person.name}}`, `{{company.name}}` and `{{answers}}`. The auto-reply cannot include what the visitor typed, because anybody can type any address into a public form. A write that leaves an email on with no recipients or an empty template, names an unknown placeholder, or names another workspace's member is `422`. A write that leaves `auto_reply` on with `require_spam_check` off is `422` and names both fields; a form stored before this rule keeps sending and is refused at its next write until the check is on. The emails go out from a background job after the submit commits, so the submit never waits for a mail server. The job writes `email_notification` and `email_auto_reply` entries to the submission's `action_log`. An entry's `status` is `ok`, `skipped`, `error` or `refused`. `error` is a failure that the job tries again, three times in about four minutes. `refused` is for these two entries only: the mail server refused the message for good (for example `550`, no such mailbox), the `detail` is its reason, and the job does not send that message again. An auto-reply is sent once per address per form in 24 hours, and at most `FORMS_AUTO_REPLY_DAILY_LIMIT` times per workspace in a UTC day. A notification to an address that is not a member's is sent at most `FORMS_EXTERNAL_NOTIFICATION_DAILY_LIMIT` times per workspace in a UTC day; above that, the message is skipped and the entry's `detail` says so. A notification to a member has no limit.

A form carries its fields, and a write carries the whole list. Positions come from the array's order. On `PATCH`, each field can carry its `id`: a field with the id of a stored field is updated in place and keeps that id. A field with no id keeps the id of a stored field it is identical to; if there is none, it is a new field with a new id. A stored field that is not in the list is deleted. An id that is not a field of this form, or an id that two fields name, is `422`. `POST` accepts no field ids. A list identical to the stored one is not a write. This matters because a stored answer is keyed by field id, and a hand-built form uses the field ids as its input names.

The handbook is a tree the caller rebuilds from `parent_id` and `sort_order`; a page's `sort_order` positions it among its siblings and means nothing across the whole set, so the list sorts by title. `PATCH` with a `parent_id` or a `sort_order` is a move, and the API renumbers both sibling sets so positions stay contiguous from 0. In the sidebar one gesture does both: dragging a page sideways indents or lifts it where it stands, and a drag that ends where it started writes nothing. It nests five levels, and a move that would push a page *or its own subpages* past that is a `422`, as is nesting a page under itself or one of its subpages. A page's `slug` is the stable handle agent tasks name pages by, so renaming a page leaves it alone; moving it on purpose is a separate field, and a collision is a `409`. Deleting a page deletes every page under it.

**An import is a dry run you then commit, and the two do not have to agree.** `POST /v1/import/jobs` parses the file, stores every row as it arrived, and plans each one against the workspace: create, update, skip, or error, with the counts and the first failing rows on the job. `POST .../commit` then re-resolves every row rather than replaying the plan, because the workspace can change in between and because rows earlier in the same file create the records later rows must match against. That is also what makes a commit idempotent — run it twice, or re-upload the same file, and the second pass finds what the first one wrote. A row that fails takes only itself down; the rest of the file still commits.

`column_map` is optional. Leave it out and the server derives one from the source pack and the file's own headers, and answers with both it and `source_headers`, so nothing has to parse CSV to build a mapping screen. A corrected mapping is a fresh job over the same file. An unmapped or blank cell is never written: a partial export with an empty Summary column would otherwise erase every summary it names.

A deal's stage resolves against this workspace's own pipeline — its slug, then its label, then the HubSpot and Salesforce alias tables — and a name that matches none of them fails the row. An export writes the slug and the major currency unit, which is what lets a Kelpie export read straight back in with no mapping at all. A missing company fails a deal row rather than creating a stub, and an `owner_email` naming nobody in the workspace fails it too, rather than quietly reassigning the deal to whoever ran the import.

**Over 500 rows a job runs in the background and the request answers `202`.** There is no durable queue: the work is a detached promise in the same process, the same way the event bus publishes. A crash mid-pass therefore strands a job in `validating` or `committing` with nothing to move it on, and the remedy is to upload the file again — which is safe, because a commit is idempotent. A real queue is the module system's job, not core's.

**Webhooks are the event bus reaching outside the process.** Registering one mints a signing secret, answers with it once, and never returns it again. Every delivery is a `POST` carrying `Kelpie-Signature: sha256=…`, an HMAC-SHA256 of the exact request body under that secret, plus `Kelpie-Event` to route on and `Kelpie-Delivery` for logs. The signature covers the body only, not the headers. The body holds the delivery `id` and `created_at`, so a receiver dedupes on the `id` in the body, refuses a `created_at` more than 5 minutes old, and compares signatures in constant time ([Verifying a signature](agents/api-and-webhooks.md#verifying-a-signature)). Delivery is at-least-once with no durable queue, the same caveat the bus itself carries, and a retry sends the same body, so a receiver can recognise one.

A non-2xx fails, and so does a redirect, which is never followed: an endpoint that moved should be seen and corrected rather than have workspace data quietly posted wherever the old address now points. Failures retry three times over about twenty seconds, and then the registration reads `failing` until an attempt lands. `paused` is the customer's own switch. `failing` is not settable — it is what the engine found, and a `PATCH` claiming it answers `422`.

Two limits keep one workspace from using the whole process. A workspace registers at most `WEBHOOK_MAX_PER_WORKSPACE` webhooks (20 unless set), and the next `POST /v1/webhooks` answers `409`. The process runs at most `WEBHOOK_MAX_CONCURRENT_DELIVERIES` deliveries at one time (20 unless set), and at most `WEBHOOK_MAX_WAITING_DELIVERIES` wait (1000 unless set). A delivery over both is not sent. Its log row has the status `failed` and `attempts: 0`, and the registration keeps its status, because the endpoint was not called.

Every verb needs the admin role, **including the reads**. A webhook URL routinely carries its own credential in the path, so listing registrations discloses a secret rather than describing a setting. That is why the Webhooks page tells a member the list is not theirs instead of showing them an empty one.

**Agent tasks are prompt recipes, and resolve is the single source of truth.** The catalog is 79 task definitions shipped in code, listed per target type. `POST /v1/agent-tasks/:task_id/resolve` loads the target, its pinned notes, open Plan items, open Decisions (confirmed ones, in `context.open_decision_ids`; Decisions no member has confirmed are in `context.proposed_decision_ids` and the prompt names them as proposals, not commitments), the handbook pages the task names (by slug, resolved to this workspace's own copies), and the related ids the data model records, and renders one markdown body under two framings: `prompt`, framed for an agent operating over MCP or REST, and `base_prompt`, the same body unframed, for an agent that returns structured operations for a caller to apply. Copy puts the framed prompt on the clipboard; Run POSTs the identical payload to a registered agent, so the two cannot drift. Each definition carries `may_create_decision` and `may_pin`. They say what a hosted AI run of the task may write: a run of a task without the permission cannot create a Decision or pin a note, whatever the model returns. They do not limit an agent that calls the API itself. A scoped API key needs more than `agent_tasks:write`: the read scope of the target type to resolve, and the write scopes of what the run may write to run. So a key cannot make an agent write a record that the key cannot write. Workspace-scoped tasks point the agent at `GET /v1/dashboard` instead of a single record, and the two sweep tasks — empty fields, and open pipeline with nothing planned — run their queries at resolve time with exact totals and honestly capped id lists.

A run records the dispatch, not the agent's work: `queued` when created, `running` while the POST is in flight, then `succeeded` on a 2xx or `failed` with the reason on anything else. A run keeps metadata only: the rendered prompt holds personal data from the target record, so the run row and `GET /v1/agent-runs` never carry it. The receiver gets it once, in the dispatch POST. One attempt, deliberately, where webhooks retry three times — re-POSTing a task risks an agent doing the whole job twice, and the human is on the page to re-run. There is no callback for an agent to report completion; what it did shows up on the records themselves, through the same API. The wire is `snake_case` throughout.

Registered agents split roles by verb, unlike webhooks: writes are admin work, but any member reads the list, because the Run dialog on every record page is built from it. The auth header is the module's one secret — sealed with `SECRET_ENCRYPTION_KEY` like a webhook's signing secret, sent as `Authorization` on each dispatch, and never returned; responses carry `has_auth_header` and nothing more. A `PATCH` that changes `endpoint` clears the stored header unless the same request gives `auth_header`, so the header is never sent to an address it was not given for. An endpoint URL with credentials in it is refused at `422`, pointing at `auth_header` instead. Deleting an agent takes its run log with it.

**The dashboard is one request, and it is the only endpoint that names records it does not return.** `GET /v1/dashboard` answers open counts for all four pipelines, overdue and due-soon plan items, partnership touchpoints at hand, contacts past the 14-day threshold, and the latest activity, notes and decisions. Two of those are questions no resource list asks — no list filters people by how long since they were contacted — and the other five would be five requests plus a client-side join.

Every attention signal is `{ total, items }`. The total counts every matching row; `items` holds what `?limit=` allowed. A page rendering four rows still says how many there are, which a capped list cannot.

Rows that point at another record carry `target_name` resolved. It is the one place in the API that does, because it is the one place where every row points somewhere different: the alternative is a request per row. A Candidate is named by the Person behind it, and a target that no longer resolves comes back `null` rather than as an id.

**Record ids in free text come back named.** An agent writing a note cites what it read: `Partnership prt_01M1…`. Notes (`body`), activities (`detail`) and the dashboard's activity and note rows carry `references`: `[{ target_type, target_id, name }]`, one entry for each record id the text holds that exists in this workspace, in the order it first appears. An id for another workspace, or for no record, is left out, so the list says nothing about records the caller cannot read. The text itself is not changed. A client finds each `target_id` in the text by string match and shows the name as a link. Activities also carry `target_name`, the name of the record the row is filed on, so a timeline can name a rolled-up row's record.

**A Note and a Decision say what wrote them.** Each carries `origin`, one of `member`, `agent`, `ai` or `unknown`. `member` is a signed-in person in the app. `agent` is a caller with an API key or an OAuth token, also when a member owns the key or approved the client. `ai` is text a model wrote: a run of the hosted AI, or the research note of person intake, which a member approves but a model writes from web pages. `unknown` is a row from before origin was recorded; no new row gets it. An author or an owner on an old row does not make it `member`, because a personal API key and an OAuth grant carry a member too. Read `agent`, `ai` and `unknown` as claims to check. The server sets `origin` from the caller. It is output only: a create or an update that sends `origin` answers `422`, on REST and on MCP. **An edit can lower it and never raises it.** When a caller that is not a signed-in member changes the `body` of a Note, or the `body` or `rationale` of a Decision, the origin becomes `agent`, unless it is `ai`, which it stays. On a Decision the same edit sets `confirmed_by_id` to `null`: the member confirmed the old text. An edit by a signed-in member changes neither, and a change to `pinned`, `due_at`, `decided_at` or `owner_id` alone changes neither. What the same edit does to `confirmed_at` depends on the scope `decisions:commit`, which the next paragraph describes. The dashboard's note and decision rows carry `origin` too.

**A Decision from an agent or from the hosted AI is a proposal until a member confirms it.** Each Decision carries `confirmed_at` and `confirmed_by_id`. A Decision that a signed-in member creates is confirmed when it is created: `confirmed_at` is the time of the write, and `confirmed_by_id` is the member. A Decision that an API key or an OAuth token creates is confirmed at once only when the credential has the scope `decisions:commit`; `confirmed_by_id` is then `null`. No preset includes that scope: not `write:objects`, not `write:all`, not `admin`. An API key with no scopes has every scope, this one too. Without the scope, and always for the hosted AI, the Decision starts with both fields `null`. It is a proposal, not a commitment, and a reader must not treat it as decided. **An agent cannot change the text of a confirmed Decision.** When a credential without `decisions:commit`, or the hosted AI, sends a `PATCH` that changes the `body` or the `rationale` of a confirmed Decision, the answer is `403` and nothing is written, also when the same request changes other fields. `decisions_update` answers the same as a tool error. The caller creates a new Decision instead, which is a proposal. The same credential can change the text of a Decision that is still a proposal, can change `due_at`, `decided_at` and `owner_id` of a confirmed one, and gets `200` with no write for a `PATCH` that sends the same text. Text is compared exactly, so a difference in white space alone is a change. Every update compares the request with the row it has locked and writes only the fields that differ. The check and the write are one transaction with a lock on the row, so a confirm that lands between an agent's read and its write cannot leave rewritten text confirmed. With the scope, the edit is written: `confirmed_at` keeps its value and `confirmed_by_id` becomes `null`, so the Decision is still listed as a commitment (`?confirmed=true`), with no member named for its present text. No write takes a confirmation off. Deleting is a separate power: `DELETE /v1/decisions/:id` needs `decisions:delete` for a confirmed Decision and for a proposal alike, and a default key or OAuth connection does not have it. `POST /v1/decisions/:id/confirm` answers `200` with the Decision; it sets `confirmed_at` to now and `confirmed_by_id` to the caller's member. The body is optional: `{ "updated_at": "…" }` is the `updated_at` the caller read on the proposal, and the confirm answers `409` when the proposal was edited after that, so a member confirms the text they read. Without it the confirm applies to whatever is there. Only a signed-in member can call it. An API key gets `403`, with any scope and also for an id that does not exist. An OAuth token gets `401`, as on all of `/v1`. There is no MCP tool for it, so no agent can confirm what an agent or a run proposed. A second confirm changes nothing and answers `200` with the same Decision, with or without `updated_at`. A Decision in another workspace answers `404`. Both fields are output only: a create or an update that sends one answers `422`, and no update confirms a Decision. `?confirmed=true` lists commitments only and `?confirmed=false` lists proposals only; the `decisions_list` tool takes the same filter as `confirmed`. The dashboard's `recent_decisions` rows carry `confirmed_at`, and so does a Decision result of `GET /v1/search`. Decisions from before the field exist as confirmed at their `created_at`.

**An activity names what it is about.** Beside the record it is filed on, an activity may carry `subject`: the record the row is about, as a reference (`{ target_type, target_id, name, parent_type, parent_id }`) with its current name. It is the note an "added a note" row records, the other end of a "linked to" or "unlinked from" row, the other record of a conversion, and the form behind a form submission. It is null when a row has none, or when the record is gone. Rows written before migration `0051` have none, except "added a note" rows the migration could match to exactly one note. The dashboard's `recent_activity` rows carry it too.

**Text can also link a record by token.** `[[type:id|Label]]`, for example `[[company:com_01M1…|Acme]]`, is a link written on purpose; it is what the note and handbook editors insert when a person types `[[` and picks a search result. `|Label` is optional. `type` is one of `person`, `company`, `deal`, `opportunity`, `partnership`, `raise`, `enquiry`, `candidate`, `event`, `attendance`, `role`, `handbook_page`, `list`, `form`, `note`, `decision` or `plan_item`. The id inside a token is found and named like any other, so a token needs nothing extra from the API: show the name from `references`, not the label, which is only what the writer saw. A token whose id is not in `references` points at a record that is gone; show its label as plain text. Plain ids of every one of those types are named too. A Note or Decision is named by its first line. A Note, Decision or Plan item has no page of its own, so its reference also carries `parent_type` and `parent_id`, the record it is on; both are null for every other type. Handbook pages carry `references` as well. `@kelpie/schemas` exports `splitRecordLinkTokens` and `formatRecordLinkToken` for reading and writing tokens.

**Today is the workspace's day, not the server's.** Overdue is a comparison between calendar dates, so the service reads `workspaces.timezone` and asks Postgres for the local day of each `last_contacted_at`. A Melbourne workspace opening the page at 9am does not see yesterday's date because the server is on UTC. The thresholds are fixed rather than settable — a "stale contact" the caller defined would mean something different in every request — and the response echoes the two it used.

**MCP is the same API through a second door.** `POST /mcp` speaks Streamable HTTP, and every tool on it is built from the Zod body, the wire mapper and the service its REST endpoint uses, so the two cannot answer differently. A tool that fails answers with the API error body — the same `404`, the same `422` and its field-level `details` — carried as a tool result rather than a protocol error, because a call that ran and refused is an answer the model should see. 146 tools today: the five verbs for each of twenty-one resources (the twelve CRM objects including Events and Attendances, pipeline stages, notes, decisions, plan items, handbook pages, forms, lists, custom fields, and consent purposes), the six convert tools, the four list-membership tools, `forms_regenerate_slug` and the three form submission tools, `event_associations_list`, the nine workspace tools (settings, team, invitations), the six webhook tools and `webhook_deliveries_list`, `search_query`, `dashboard_get`, `tags_list`, `activities_list`, `sample_data_install`, and the five import/export tools.

The endpoint takes **bearer keys only**, and deliberately not the session cookie the REST surface accepts. Three things keep a cross-origin browser out: a present `Origin` that is not this deployment's own answers `403`, no CORS headers are sent, and there is no ambient credential to spend even if one got through. There is no session id and no server-initiated stream, so `GET` and `DELETE` answer `405` and any instance can answer any request.

**It speaks `2026-07-28`, `2025-06-18` and `2025-03-26`, and serves two eras on the one endpoint.** `2026-07-28` removed the `initialize` handshake: a modern client puts its protocol version, identity and capabilities in every request's `_meta`, mirrors the method and tool name into `Mcp-Method` and `Mcp-Name` headers, and gets back `resultType: "complete"`, the server's identity in the result's `_meta`, and `ttlMs`/`cacheScope` on anything cacheable. Everything before that revision opens with `initialize`, and the spec calls those *legacy*.

The endpoint decides which it is being asked for from the request itself: a `_meta` protocol version or a `server/discover` means modern, anything else means legacy. A legacy client keeps `initialize`, `ping` and its JSON-RPC batches (at most 20 messages in a batch, and each message spends one unit of the API rate limit); a modern one gets `server/discover`, which the revision makes mandatory, and none of those three, which it removed. A version Kelpie does not speak is refused with `-32022` carrying the list it does, so a client can pick another and retry rather than being told only that it failed.

For a modern request the mirrored headers **must** agree with the body — `MCP-Protocol-Version` with the `_meta` version, `Mcp-Method` with the method, `Mcp-Name` with the tool — and a disagreement is `400` with `-32020`. The point is that an intermediary routes on the header while the server executes the body, so the two differing is the bug worth refusing. `Mcp-Name` is decoded from the `=?base64?…?=` sentinel before the comparison. A method the revision does not have answers `404` rather than `200`, which is how a client tells a modern server lacking a method from a legacy server that does not host the endpoint at all.

Three REST operations have no tool. Creating a workspace and accepting an invitation both need a browser session, and a key issued for one workspace could not act on the new one anyway. Deleting a workspace destroys everything the calling key is scoped to, and its slug confirmation is no safeguard against an agent that can read the slug. API keys have no tools at all: a key that can mint keys is an escalation nothing in the brief asks for.

`export_csv` inlines the file and refuses over 256 KB, naming `GET /v1/export/{object}.csv` instead. A truncated CSV looks exactly like a whole one, and an agent would draw conclusions from the rows that were not there.

**Lists are typed collections, and the type is load-bearing.** A list's `target_type` is fixed at creation; a member of another type is `422`, and a composite foreign key enforces the same rule underneath the service. Member rows carry `target_name` resolved, like dashboard rows, and `GET /v1/list-memberships` answers `404` for a record that does not exist rather than an empty set.

**Pipeline conversion creates a new record and keeps the source.** `POST /v1/{enquiries|deals|opportunities|raises|partnerships}/:id/convert` takes `{ target_type, stage_id?, company_id?, kind?, name? }` and answers **201** with the full target record. Notes, activities, decisions, plan items, form attach targets, and agent runs repoint to the target; person links copy (the source keeps its own). Custom fields intersect by definition key on the target type; list memberships drop when the type changes. The source gets `converted_to: { target_type, target_id }` and moves to the first closed stage of its kind. A second convert on the same record is **409**. Enquiries still accept an empty body and default to deal; `converted_deal_id` remains when the target is a deal. A scoped API key or OAuth token needs the write scope of the source and of the target type, on REST and on the convert tools; without the target's it answers **403** and converts nothing.

**Sample data adds the fixture next to existing records.** `POST /v1/workspaces/:id/sample-data` writes the fixture in one transaction and answers the counts. Existing companies and people stay. A sample email or domain that is already present is `409`. The installer skips rows for a toggleable module the workspace has switched off. The onboarding modules step offers it as a checkbox; Admin → Data carries the same button and asks for confirmation before it writes.

Underneath: the module runtime with its credentialled and public route contributions, a typed event bus with per-module catalogs and after-commit publication, the entitlements registry (including the `workspace.access` gate on `/v1` and `/mcp`), the `Idempotency-Key` middleware, four rate-limit budgets, 48 tables with migrations, and an integration harness that creates its own database per test worker and empties it between cases.

Passwords are argon2id. Session, invite, reset, and API key secrets are stored as SHA-256 hashes. A webhook signing secret is the one credential that is encrypted rather than hashed, because signing a delivery needs it back; `lib/secrets.ts` seals it with AES-256-GCM under `SECRET_ENCRYPTION_KEY`. Credentials arrive as either a session cookie or a `Bearer kp_live_…` / `kp_user_…` key. `/mcp` also takes a `Bearer kp_oat_…` OAuth access token, and `/v1` answers `401` to one.

**OAuth sign-in for MCP clients.** Core's `oauth` module is an OAuth 2.1 authorization server for one resource, this deployment's `/mcp`. A client that connects only through OAuth (a Claude.ai connector, say) needs only the endpoint URL. The `401` from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata="…", scope="read:objects write:objects"`; the client reads the protected resource metadata, then the authorization server metadata, identifies itself with a Client ID Metadata Document or Dynamic Client Registration, and sends the person to `/oauth/authorize`. That redirects to the UI's consent page at `/consent/:request_id`, where the person chooses one or more workspaces and may remove requested scopes. A client that names no scope gets `read:objects write:objects`, which gives no delete and no handbook write. **Sensitive scopes are shown apart and start clear.** A scope is sensitive when it gives a delete, a handbook write or `decisions:commit`, by its own name or through a preset, so `people:delete`, `delete:objects` and `write:all` all are. `GET /v1/oauth/requests/:id` names them in `extra_scopes`: each requested sensitive scope, then `decisions:commit`, `handbook:write` and `delete:objects`, which the person may add though the client did not ask. A requested preset that holds a sensitive scope is in that list whole. Each workspace in the answer carries `connected`, true when this person has a grant to this client there, and `held_scopes`: the `extra_scopes` that grant gives already. The page opens with the connected workspaces ticked, or with the workspace of the session when there is none, and starts a sensitive scope ticked only when each selected workspace holds it. **A local client gets none of this.** A local client is one whose redirect is not HTTPS: a loopback address, which matches on any port, or a private-use scheme, which a second program can register too. Neither proves which program on the computer asked. Most desktop MCP clients are local clients. The answer for one has `local_client` true, every `connected` false and every `held_scopes` empty, whatever the grants hold, so the page opens as for a new app: the workspace of the session, every sensitive scope clear. Each workspace also carries `display_connected` and `display_held_scopes`, which hold the real facts for every request. They are for showing only: the page marks a workspace "connected now" and a row "allowed now in" its workspaces, and ticks nothing from them. The consent endpoints answer a signed-in session only, with that person's own grants to that client, so the program that opened the request cannot read them. An earlier connection of a local client stays in place until it is revoked or an approval for the same workspace replaces it. One approval joins this client's connections for the approved workspaces into one, and the tokens of the others end. A sensitive scope that the request does not name and that is not one of the three always-offered ones is not on the page, so a connection that holds it loses it at that approval. `POST /v1/oauth/requests/:id/approve` accepts the requested scopes and those three, and answers `422` to any other scope. **An approval replaces the scopes of the connection**: the token response and the stored grant carry what the person approved that time and nothing from before, so a client that connects again must ask for every scope it wants to keep. A refresh can narrow the scopes but not widen them. The code exchange requires PKCE (S256). Access tokens last one hour; refresh tokens rotate on each use and a reused one ends the connection. A connection is one approval, with one grant for each workspace the person ticked. A grant acts as its user, in one workspace, narrowed by its scopes, which are the API key scopes. A connection with one workspace needs nothing more. A connection with more than one gets a mandatory `workspace_id` argument on each tool and a `workspaces_list` tool that gives the ids; a call that names no workspace is refused, and there is no default. A tool call the scopes do not cover answers `403` with `error="insufficient_scope"`; its `scope` names what the token holds and then what is missing, so a client that asks for that list keeps what it had. Codes, tokens and client secrets are stored as SHA-256 hashes. The issuer and resource come from `APP_BASE_URL`. Account → Connected apps lists the grants, each with `extra_scopes` (the sensitive powers its scopes give, under any name), removes one workspace from a connection (`DELETE /v1/oauth/grants/:id`), and ends a whole connection (`DELETE /v1/oauth/connections/:id`).

**OAuth errors and redirect URIs.** `GET /oauth/authorize` redirects to the consent page or answers `400` with an HTML error page. It does not redirect to the client with `error=…`: a bad `response_type`, `scope`, `resource` or PKCE parameter stops on that page, which shows the OAuth error code. The client receives `error=access_denied` at its redirect URI only when the person selects Deny. A redirect URI must be `https:`, or `http:` on `localhost`, `127.0.0.1` or `[::1]`, or a private-use scheme: a reverse domain name with a dot (`com.example.app:/callback`), or `cursor:`, `vscode:`, `vscode-insiders:` or `windsurf:`. Registration answers `400 invalid_redirect_uri` to any other scheme. A Client ID Metadata Document that cannot be fetched or is not valid gives one fixed message for every cause; the cause is in the server log. At `POST /oauth/token`, a request with a wrong `code_verifier`, `redirect_uri` or `resource` answers `400` and leaves the code unspent until it expires after 60 seconds. `Authorization: Basic` credentials that cannot be read answer `401 invalid_client` with `WWW-Authenticate: Basic`. Operator detail: [Security](self-hosting/security.md#oauth-sign-in-for-mcp-clients).

In the browser, the port is complete: Dashboard, search (a header box and `/search`), a workspace switcher in the header, People, Companies, Hiring, Events (list, month calendar, and detail), the four pipelines with their stage settings, Lists, Planning, Decisions, Forms, Handbook, the admin pages (Workspace, Team, Data with import/export and the sample-data installer, API keys, Webhooks, MCP, Modules), the account pages (Profile, Security, Preferences, personal API keys, Connected apps), the OAuth consent page, and the full auth flow from signup through email verification, onboarding, password reset and invitation acceptance. Detail pages render the record-tab slots on the main record types including Event, and the sidebar renders module nav items, so a UI module has somewhere to land from the start.

Forms have a list and a four-tab detail page: submissions with links to what each one created, a drag-ordered field builder, settings, and the embed snippets. The builder is the one screen in the app that saves explicitly rather than per keystroke, because a write replaces the whole field list and committing on every character would reissue every field id. It refuses to send a list the API would reject, and shows why beside the field responsible.

Workspace administration is under Admin in the sidebar. **Workspace** carries name and timezone. Deleting it takes the workspace name typed as confirmation.

**Team** invites by email, changes roles, and removes members. Every rule is the API's, not the page's: a member who tries anyway gets `403`. The owner cannot be demoted or removed, and ownership moves only by being given away, which makes the outgoing owner an admin in the same transaction. Removing somebody who still owns Deals, Opportunities, Partnerships, Raises, Events, Plan items, Decisions or Notes answers `409` naming each type and how many, because the delete is restricted; reassign them first. An invitation's status is derived from `expires_at` rather than stored, so a stale one reads as expired with nothing sweeping the table. The invitation email goes out from a background job. `email_failed_at` and `email_failure` on an invitation are `null` while the email is on its way or was sent. They hold the time and a short reason (one line, at most 300 characters) when the email was not delivered: the mail server refused it for good, or the last retry failed. The Team page shows "Email not delivered" with the reason. Resending issues a new token and retires the old link, and sets the two fields back to `null`; so does a later send that works. Revoking deletes the row, which is what actually kills the link already in somebody's inbox.

Deleting a workspace is the owner's alone and takes the slug as confirmation, in the request rather than only in the browser, so an accidental `DELETE` at the right id does nothing. It cascades every table that carries a `workspace_id`. Accounts are global and survive it.

The emailed invitation lands on `/join?token=…`, which accepts as the signed-in account. Signing in from there returns to the invitation instead of the CRM.

## Known gaps

- **Two UI slots with no render site.** `record.sidebar.<objectType>` and `dashboard.cards` are registered, typed, and collision-checked, and no core page renders either yet. Record tabs render on the main record types including Event; `role` and `candidate` are in the type list without a render site. A candidate is also a target with no detail page, so a candidate row in Decisions or Planning shows a type label rather than a link, and a decision, note or plan item on a candidate links nowhere.
- **Role enforcement outside workspace administration.** Administration is gated at `admin`, and API keys already were. Every CRM resource is open to any member, which is what the specs describe; no document defines a read-only role. Narrowing that is a product decision, not a missing check.
- **MCP tools for agent tasks.** `run_agent_task` is deferred (not required for v0), so the resolve, run, runs and agents endpoints have no tools and the count stays at 121. An agent that wants a context pack can still be handed one: Copy the prompt, or POST resolve over REST with its key.
- **An agent reporting a run's outcome.** A run's lifecycle is the dispatch — `queued`, `running`, then `succeeded` or `failed` with the reason. No spec defines a callback for the agent to say it finished the work, so nothing pretends to know; the work itself lands on the records through the ordinary API.
- **Notification email.** The Preferences page stores a weekly digest, mention and product-update choice per account, and nothing sends any of them: email sending is a v0 non-goal, and the email port serves invites, password resets and verification only. The page says so on screen rather than leaving a reader to infer a capability from a toggle.
- **Locale loose ends.** Dates now format in the stored timezone (account preference, then workspace, then UTC) with the browser's locale. Still fixed: money formats under a hardcoded `en-US` locale, and the Team page renders dates in the browser's zone rather than the workspace's. Timezone pickers (Person, Event, workspace settings, account preferences) search the full IANA set.
- **A friendly device name on the Security page.** A session records the raw `User-Agent` and shows it, so a browser reads as a long string rather than "Chrome on macOS". `location` is never populated at all and renders "Unknown"; nothing derives one from a request.
- **Leaving a workspace, and the last owner.** An admin can remove themselves; the owner cannot, and has to hand ownership over first. An owner who is the only member has no way out except deleting the workspace.
- **Webhook polish**, deferred in v0. Four events are deliverable and the rest of the catalogue is not offered, rather than accepted and never sent. Retries live in the process, so a crash mid-backoff loses that delivery. The delivery log keeps `WEBHOOK_DELIVERY_RETENTION_DAYS` of history (30 unless set), pruned in the transaction that records the webhook's next delivery because there is no scheduler in core — so a hook that stops delivering keeps its last window of rows until the hook or workspace is deleted. The log is on the Webhooks page, but `payload` is a `jsonb` column and Postgres reorders its keys, so it shows the content of a body and not the exact text `Kelpie-Signature` was computed over.
- **A fifth wire event kind.** Since the 0.6.0 event catalogs, a module makes its own event deliverable by naming it with a `created`/`updated`/`deleted` suffix and a record target type, and the bridge translates it to the matching `record.*` wire event — no builder needed. What a module still cannot do is add a wire kind beyond the four the catalogue advertises; wider wire coverage is a follow-up. See [Events](extending/writing-a-module.md#events) in the module guide.
- **Outbound egress filtering is a flag, not a policy.** `BLOCK_PRIVATE_EGRESS=true` refuses webhook and agent-dispatch URLs that resolve to private addresses, and defaults off because a self-hosted install legitimately posts to `http://automation.internal`. A hosted deployment still wants network-level egress policy behind it.
- **A CI workflow.** The scripts are ready and `npm run release` runs all of them; nothing runs them on push.
- **The MCP server's advertised version.** `MCP_SERVER_INFO` hardcodes `version: '0.0.0'` rather than the package version, so a client reading the identity sees a number that lags every release.
- **A copyright line in `LICENSE`.** `CLA.md` names the copyright holder (Christopher Skene) and `CONTRIBUTING.md` makes opening a PR the assignment agreement, which is what proprietary cloud modules on an AGPL core require. `LICENSE` itself is still the verbatim AGPL-3.0 text with the FSF's unfilled template at the bottom; no copyright notice names the project.
